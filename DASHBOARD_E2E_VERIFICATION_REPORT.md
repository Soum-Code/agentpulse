# Dashboard End-to-End Verification and the Trace-to-Dataset Loop

**Date:** 2026-08-24
**Method:** Real backend + dashboard dev servers, a real trace pushed through the actual SDK (`scripts/e2e_dashboard_demo.py`), driven through the browser UI exactly as an operator would, cross-checked against direct backend API calls and a direct SQLite query at each step.

## 1. Why this wasn't a rubber-stamp pass

The previous session's dashboard redesign (`240b313`, `a44c859`) fixed a set of real bugs found by comparing the UI against the running backend (WebSocket route mismatch, missing `ws: true` on the Vite proxy, fabricated benchmark numbers baked into static views). This pass pushed further: instead of loading already-cached pages, it ingested a fresh trace and clicked through the operator workflow that trace was supposed to enable (see an alert, curate it into a dataset, confirm it's retrievable). That workflow surfaced four more real bugs, none of which were visible just by loading the dashboard and looking at it.

## 2. Bugs found and fixed

**Headline stat tiles frozen at 0 in any background tab.** `useCountUp` (`dashboard/src/components/ui.tsx`) animates each stat via `requestAnimationFrame`. Every major browser suspends `rAF` entirely for hidden/unfocused tabs to save resources — confirmed directly (`document.visibilityState: "hidden"`, an `rAF` callback that never fired within 2 seconds). Since the hook's initial state defaults to 0 and only ever advances inside the `rAF` callback, any tab that isn't the focused one shows Composite Risk, Total Traces, Open Incidents, and Active Agents permanently stuck at 0 — for a monitoring dashboard, which is routinely left open in a background tab, this silently hides exactly the numbers it exists to surface. Confirmed the underlying data was correct the whole time (the adjacent `Meter` bar, which reads the raw value directly rather than through the animated hook, showed the true 69% risk width even while the number above it read 0.000). Fixed by skipping the animation and jumping straight to the real value when `document.visibilityState === 'hidden'`, mirroring the existing `prefers-reduced-motion` path.

**CORS preflight rejected by the API-key middleware, breaking every cross-origin request.** Starlette wraps middleware in reverse registration order — the last one added is outermost and runs first. `backend/app/main.py` registered `CORSMiddleware` first (innermost) and `APIKeyMiddleware` after it (outermost), so `APIKeyMiddleware` intercepted `OPTIONS` preflight requests and rejected them with 401 before `CORSMiddleware`'s own preflight short-circuit ever ran. Preflight requests never carry custom headers like `X-API-Key` by spec, so this made any cross-origin caller fail regardless of whether it had a correct key. Reordered so `CORSMiddleware` is added last (outermost).

**Dashboard writes 401 unconditionally — `VITE_API_KEY` was never documented.** `dashboard/src/lib/api.ts` only attaches `X-API-Key` when `VITE_API_KEY` is set, and neither `.env.example` nor any `dashboard/.env` set it, so every mutating dashboard action (curate case, and presumably any future write action) failed silently — the UI showed no error, it just did nothing. Added `VITE_API_KEY` to `.env.example`'s Dashboard section and created a local `dashboard/.env` for testing (gitignored, not committed).

**The trace-to-dataset loop only worked halfway.** `POST /v1/datasets/{name}/cases` (the "Curate case" action) writes to the `dataset_cases` SQL table, but `GET /v1/datasets/{name}` only ever read static JSON files from `datasets/`. A curated case saved successfully and immediately 404'd when read back — there was no bridge between the write path and the read path for anything other than the three pre-shipped file-based splits (dev/val/test). Fixed `backend/app/routers/experiments.py`: `GET /v1/datasets/{name}` now falls back to querying `dataset_cases` by `dataset_version` when no matching file exists, and `GET /v1/datasets` now also lists DB-only dataset versions (like `v1.0_curated`) alongside the file-based ones.

All four fixes were exercised through the real UI, not just unit-tested: a trace was ingested, its alert appeared in the Incident Inbox, "Curate case" was clicked, the modal was submitted, and the resulting row was confirmed with a direct `sqlite3` query against `data/agentpulse.db` (`dataset_cases.id = 13`, correctly linked to the real `trace_id`/`span_id`) and then read back successfully through `GET /v1/datasets/v1.0_curated`. `pytest tests/ -q` was re-run after the backend changes: 99/99 passing, no regressions.

## 3. Found, not fixed: Agent Topology and Trace Waterfall are still 100% static

The prior session's handoff already flagged this as worth checking. It's now confirmed with direct evidence rather than suspicion: two different real traces were ingested, with different agent names, different risk scores, and different trace IDs, and the "Agent Execution Topology" and "Active Trace Waterfall" sections on the Overview page rendered byte-identical content both times (`tr_e2e_research_48821`, "Query Planner" / "Paper Indexer" / "Claim Verifier" / "Synthesis Engine" / "Report Author"). These are hardcoded fixtures (`SAMPLE_WATERFALL_SPANS` and similar in `App.tsx`), not wired to the live `agents`/`traces` state the four stat tiles correctly use. Rewiring them to aggregate real per-agent stats and render a real waterfall from live span data is a meaningfully larger feature build than the fixes above (the fixtures currently encode a specific illustrative narrative — a research pipeline with a deliberately fabricated citation — that a live version would need to reconstruct generically from arbitrary trace shapes), so it wasn't attempted in this pass. Left as an open item.

## 4. Scope not covered here

This exercised the incident-triage-to-dataset path specifically. It did not touch the Replay Debugger, Drift & Stability, Experiments, or Telemetry Lab pages, which may have their own live-vs-fixture gaps not yet checked with real data the way this pass checked Overview and Incidents.
