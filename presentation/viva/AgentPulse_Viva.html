TIME: 1:10-2:15 (65 seconds) SAY: - Read the boxes from left to right. This is the path of one step ("span") of an agent. - The SDK sits inside your agent. It sends each step to AgentPulse and never waits for an answer, so the agent is never slowed down. - The API only puts the step in a queue. A separate worker picks it up and runs two small models: MiniLM (turns text into numbers, called embeddings) and DeBERTa (an NLI model: it says if one text supports or contradicts another). - If a score crosses a threshold, an alert is raised. The same alert for the same agent comes at most once in 15 minutes. - The console shows everything live. If something was not measured, it shows a dash, never a fake zero. IF ASKED "What is a span?": One step of an agent: one LLM call or one tool call, with its input, output and timing. SourceGROUNDING_RECALIBRATION_2026-10.md, section 3.6 and tables T3c, T3d (analysis 2026-10-22); HOW_IT_WORKS.md, the verdict rule; backend/app/services/grounding.py (NEUTRAL_RISK_WEIGHT = 0.3).
TIME: 2:15-3:45 (90 seconds) SAY: - Grounding means: is the answer supported by the evidence the agent had? An NLI model (natural language inference) reads the two texts and gives three probabilities: supports, contradicts, or neutral (says neither). - Our risk is contradiction plus 0.3 times neutral. 0 is safe, 1 is risky; above 0.4 is medium, above 0.7 is high. The 0.3 is my design choice, not a fitted number: any weight from 0 to 0.3 gives the same result on our data. - Next to the score we show a verdict. "Unverifiable" means the evidence neither supports nor contradicts. It is not a pass; it means "could not check". - Result on 68 hand-labelled cases: on the 30-case test split F1 is 0.963 (F1 = "finds the failures and does not cry wolf"; 1.0 is perfect), and only 1 of 17 correct answers was wrongly flagged. On 47 cases never used for design, F1 is 0.927 or 0.952. - Honest point: this is a small sample, and 5 test cases copy development cases. It is not a production benchmark. IF ASKED "Why 0.3 and not 0.5?": At 0.5, 7 of 17 correct test answers were wrongly flagged medium; at 0.3 only 1 of 17 (backup slide B1). IF ASKED "Is 68 cases enough?": No, not for a general claim; the 95% interval on the test F1 is 0.897 to 1.000, and more labelled data is my first next step. SOURCES: GROUNDING_RECALIBRATION_2026-10.md (banner, finding 4, section 3.6; T3c: F1 0.963, FPR 0.059 = 1/17, 5 of 30 copy dev; T3d: held-out 47, F1 0.927 at 0.7 and 0.952 at 0.4, FPR 0.074 = 2/27; T3b: interval [0.897, 1.000]; analysis 2026-10-22); HOW_IT_WORKS.md "The verdict, next to the score"; grounding.py NEUTRAL_RISK_WEIGHT = 0.3 (PR #89). Model: cross-encoder/nli-deberta-v3-small.

SourceDRIFT_REAL_TEXT_DIAGNOSIS_REPORT.md, sections 11.3 and 11.5 (2026-08-27); HOW_IT_WORKS.md (baseline 20, window 12, threshold 0.30).
TIME: 3:45-4:25 (40 seconds) SAY: - Drift compares an agent with its own past, not with a correct answer. - MiniLM turns each answer into a vector (a list of numbers). We average the agent's first 20 answers (baseline) and its latest 12 answers (window). - If the two averages are far apart (cosine distance above 0.30), we raise "drift detected". - On real traces it caught 91.9% of drift, with 1.5% false alarms. - But only 24.5% of real sessions had enough answers (32) to measure at all. That is the honest weak point. IF ASKED "What happens to short sessions?": They get no drift value; the console shows a dash, not zero. SOURCES: DRIFT_REAL_TEXT_DIAGNOSIS_REPORT.md 11.3 and 11.5 (2026-08-27, offline, held-out split of an external real-trace corpus, measured once); HOW_IT_WORKS.md; README "What it does" (32 outputs).

SourceLLM_JUDGE_COMPARISON_REPORT.md, median latency table and correction banner (2026-08-26; F1 at the shipped weight derived from stored probabilities).
TIME: 4:25-5:10 (45 seconds) SAY: - Can we afford to check every step? Yes. Our two models took 202.94 milliseconds per case. - A local 8-billion-parameter LLM judge took 3,170.39 milliseconds. That is 15.6 times slower. - To be fair: on the same 30 cases the judge was more accurate, F1 1.000 against our 0.963. - So the trade is a little accuracy for a big saving in time and cost. That saving is what lets us score every span. - This is one judge model on one machine, so I do not claim it for every LLM judge. IF ASKED "Why not use the judge then?": It is 15.6 times slower and needs a large model or a paid API call per span; checking every span is the point of this project. SOURCES: LLM_JUDGE_COMPARISON_REPORT.md (median 202.94 vs 3,170.39 ms, 15.6x; judge Qwen3-8B-GGUF Q4_K_M via llama.cpp, CPU; 2026-08-26). F1 1.000 vs 0.963 at weight 0.3: the report's correction banner, derived from stored probabilities, not re-run. Other single-run latencies (not on the slide): MiniLM 15.1 ms and DeBERTa 88.5 ms P50 (benchmarks/benchmark_results.json, 2026-08-18); 151.19 / 165.18 ms per case (experiments/results/ablation_results.json, 2026-09-18); live median 180 ms over 172 spans (docs/E2E_TEST_2026-10-27.md item 23).
