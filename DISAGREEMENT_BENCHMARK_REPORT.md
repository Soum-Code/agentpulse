# Inter-Agent Disagreement Engine: Benchmark and Rebuild

**Date:** 2026-08-26
**Component:** `backend/app/services/disagreement.py`
**Dataset:** `datasets/v1.0_multiagent.json` — **a constructed benchmark dataset, not production-collected** (construction methodology in §2)
**Script:** `experiments/disagreement_benchmark.py`
**Raw results:** `experiments/results/disagreement_benchmark_results.json`
**Models confirmed loaded at run time:** `{nli_model: true, nli_tokenizer: true, embedding_model: true}`

---

## 1. Why this work happened

`THRESHOLD_ANALYSIS.md` §2 (Observation 2) and §4 record that ablation Config E
(NLI + inter-agent disagreement) "produced metrics identical to Config B (NLI only),
i.e. the additional signal never changed a decision on this dataset." The reason is
structural: `datasets/v1.0_dev/val/test` cases are single-agent (evidence + one claim),
so the only pair available to a cross-agent engine is (evidence → claim) — the same
comparison Config B already makes. **The disagreement engine was therefore never
actually exercised by any existing measurement.**

The state of the component before this work:

- 79 lines, one function, one NLI call.
- `tests/test_disagreement.py` contained 2 disagreement tests, and **both asserted
  `None`** (same-agent skip, empty-text skip). No test proved the engine ever detected
  a contradiction. This was structural rather than negligent: no test in this repository
  loads evaluation models, so `compute_nli_grounding` returns `None` under pytest and
  the engine short-circuits before reaching any detection logic.
- No benchmark existed (tool-claim validation has one; drift has
  `DRIFT_EXPERIMENT_REPORT.md`; disagreement had nothing).
- `evaluator.py` compares each span only against its immediate upstream agent, in one
  direction.

This matters beyond internal coverage: inter-agent disagreement is one of the three
signals AgentPulse claims as a differentiator against MLflow, Arize, and Datadog, none
of which ship cross-agent contradiction detection as a first-class feature. It was
simultaneously the least-evidenced part of the codebase.

## 2. Dataset: construction methodology and its limits

`datasets/v1.0_multiagent.json` is a **constructed benchmark dataset, purpose-built to
exercise inter-agent disagreement detection.** It was not collected from production
traffic, not sampled from real agent deployments, and not generated by running the demo
workflows. Every case was hand-written for this benchmark.

**Construction method.** 22 cases across three domains (research, support, analytics).
Each case is a sequence of 2–4 agent outputs representing one trace. Ground truth is
assigned at construction time, not by annotation of observed behaviour: a case is
labelled `expected_disagreement: true` if it was *written to contain* a specific factual
conflict between two named agents, recorded in `contradicting_pair`, and `false` if it
was written to be internally consistent. The `adjacent` field records whether that
conflicting pair is consecutive in the trace — the discriminating property, since the
shipped engine can only compare consecutive agents.

Case categories, and what each is for:

| Category | Cases | Purpose |
| :--- | :---: | :--- |
| Adjacent contradiction | 3 | Baseline capability — conflicts the shipped wiring *can* see |
| Non-adjacent contradiction | 4 | Conflicts between agents the shipped wiring never compares |
| Negation contradiction | 2 | Explicit polarity flips ("was released" / "was never released") |
| Agreement (true negative) | 4 | Restatements of the same fact — must not fire |
| Paraphrased agreement | 3 | Same fact, different wording — over-trigger control |
| Different topic, not contradiction | 2 | Unrelated outputs — over-trigger control |
| Partial refinement | 1 | "roughly four thousand" vs "4,187" — precision, not conflict |
| Implicit contradiction (written as expected-misses) | 3 | Conflicts requiring inference, written to keep recall honest |

**Limitations of this dataset, stated plainly:**

- **Constructed, so it measures the engine against intent, not against reality.** Real
  agent outputs are longer, noisier, and mix multiple claims per output. These cases are
  short and each carries one clear proposition. Absolute scores here will not transfer
  to production traces.
- **Author bias.** The same person wrote the cases and the fixes in §4. The three
  "implicit contradiction" cases exist specifically to counter this (see §6), following
  the precedent set in `TOOL_CLAIM_VALIDATOR_REPORT.md` §3, but this does not eliminate
  the bias — it only makes it visible.
- **22 cases is a small sample.** One case moves precision or recall by roughly 0.03–0.08.
  Differences of that size between configurations below should not be treated as
  meaningful separations.
- **No dev/test split.** With 22 cases there is not enough data to select a threshold on
  one split and report on another, which is the methodology `THRESHOLD_ANALYSIS.md`
  establishes for this repository. Consequently **no threshold in this work was fitted to
  this dataset** — see §4.1.

## 3. Baseline: the engine as originally shipped

Run against **completely unmodified engine code** (verified with `git status backend/`
immediately before execution — no changes staged or unstaged). This ordering is
deliberate and follows `TOOL_CLAIM_VALIDATOR_REPORT.md` §1: benchmarking first, then
fixing only what the benchmark demonstrates, avoids a self-fulfilling result where the
test set is built from cases the fix was designed to catch.

| Metric | Baseline (adjacent-only, no gate) |
| :--- | ---: |
| Precision | 0.769 |
| Recall | 0.833 |
| F1 | 0.800 |
| FPR | 0.300 |
| TP / FP / FN / TN | 10 / 3 / 2 / 7 |

### 3.1 Two failure modes, separated by diagnostic

The benchmark scores the labelled conflicting pair directly — in both directions — as a
diagnostic that does **not** feed the headline metrics. Its purpose is to distinguish an
*architectural* miss (the pair is never compared) from a *model* miss (the pair is
compared and NLI fails to detect it). Only the former would justify changing the
comparison architecture.

Result: **all 12 labelled conflicting pairs scored above threshold when compared
directly** (forward detection 12/12). Every miss was therefore architectural, not a model
limitation:

- `ma_06` — labelled pair (triager ↔ escalator), "low-severity cosmetic issue affecting
  no production users" vs "high-severity outage affecting all production users". Scores
  **1.000** when compared. The shipped wiring compared only (triager↔investigator) at
  0.002 and (investigator↔escalator) at 0.006, and flagged nothing.
- `ma_07` — labelled pair (collector ↔ summarizer), "revenue decreased by 12%" vs
  "revenue increased by 12%". Scores **1.000** when compared, never compared in practice.

### 3.2 The headline recall was inflated by accidents

Two further cases — `ma_04` and `ma_05` — counted as true positives while the engine
fired on **a different pair than the labelled conflict**:

- `ma_04`: labelled conflict is (loader ↔ reporter), "4,200 rows after deduplication" vs
  "15,000 rows after deduplication". The engine instead fired on (loader ↔ transformer)
  at 0.985 — "4,200 rows after deduplication" against "applied normalization and type
  coercion to every column", two statements that are entirely compatible.
- `ma_05`: labelled conflict is (planner ↔ writer); the engine fired on (analyst ↔ writer).

Both are the right answer for the wrong reason. Measuring strictly — a labelled conflict
counts as detected only if the engine flags it *on the labelled pair* — gives:

**Strict recall 0.667, against a headline recall of 0.833.**

### 3.3 The dominant problem was precision, and it was not in the plan

The three false positives share one cause: **DeBERTa NLI reports high contradiction
probability for agent outputs that are merely about different subjects.**

| Case | Agent outputs | Similarity | Contradiction |
| :--- | :--- | ---: | ---: |
| `ma_15` | planner "decompose into three sub-questions" vs retriever "retrieved four documents" | 0.276 | **0.999** |
| `ma_16` | triager "assigned ticket to platform queue" vs investigator "collected 500 lines of error log" | 0.174 | **0.975** |
| `ma_13` | "went down shortly after the 14:00 deployment" vs "outage began just following the deploy that shipped at 2 PM" | 0.647 | **0.984** |

`ma_13` is not even a topic mismatch — it is the *same fact in different wording*, scored
as a near-certain contradiction.

This is more damaging in production than the architectural gap. In a real multi-agent
pipeline, consecutive agents almost always do different jobs — a planner plans, a
retriever retrieves — so an ungated contradiction score fires on the common case rather
than the exceptional one. This finding was not anticipated when the work was planned; it
came out of the baseline run.

### 3.4 Bidirectional NLI: considered, and rejected on evidence

NLI is not symmetric — `compute_nli_grounding(A, B)` need not equal `(B, A)` — and the
engine computes only one direction. The benchmark measured whether this causes real
misses.

It does not. Forward detection caught 12/12 labelled pairs; reverse caught 11; cases
detected **only** in reverse: **0**. Asymmetry is real and sometimes large (`ma_19`:
forward 1.000, reverse 0.088, a gap of 0.912) but never produced a false negative on this
dataset.

**Bidirectional evaluation was therefore not implemented.** A theoretical property is not
sufficient justification for a change that would double NLI cost per pair.

## 4. Changes made, and why each one

Two changes, both justified by §3, implemented additively — the existing
`evaluate_inter_agent_disagreement` signature is preserved, so `evaluator.py` and the
pre-existing tests continue to work unchanged.

### 4.1 Relevance gate

A contradiction probability is only trusted when the two outputs are topically related.
Below a similarity floor the pair is treated as addressing different subjects rather than
conflicting. The raw score is still returned — gating suppresses the flag, not the
evidence.

Reuses the existing `compute_semantic_similarity` (MiniLM) from `grounding.py` rather
than introducing a new model or dependency.

**On the threshold value — this is the weakest part of this work and is not hidden.**
`RELEVANCE_FLOOR = 0.40` reuses `grounding.py`'s existing `STAGE1_RISK_THRESHOLD`, chosen
independently for the cascade's low-similarity floor. It was **not** fitted to this
dataset, because 22 cases with no dev/test split cannot support threshold selection
without selecting on the test set.

The honest consequence is that **0.40 does not cleanly separate the two classes on this
data**: the lowest-similarity genuine contradiction sits at 0.433 (`ma_21`) and the
highest-similarity false positive at 0.647 (`ma_13`). The margin below the floor is
roughly 0.03. The gate removes 4 of 5 measured false-positive firings; it does not remove
all of them, and an independent, larger dataset is required before 0.40 can be described
as validated.

The gate **fails open**: if the embedding model is unavailable, `compute_semantic_similarity`
returns `None` and evaluation proceeds ungated rather than silently suppressing every
disagreement signal. This matches `grounding.py`'s stated fail-open policy and is the
safer direction for a monitoring system — over-reporting is recoverable, silently
reporting nothing is not. This is the exact failure shape that wasted a 9-hour Kaggle run
documented in `PROJECT_REPORT.md` §4.

### 4.2 Trace-level N-way comparison

New `evaluate_trace_disagreements()` compares every agent pair in a trace rather than
only consecutive ones, and aggregates. The per-span function is unchanged and still used
by `evaluator.py`; N-way is for callers holding a whole trace. (The live pipeline reaches
the same coverage a different way — incrementally, per arriving span — see §9.)

Cost is O(N²): 5 agents is 10 comparisons, 10 agents is 45, each running one NLI plus one
embedding forward pass. A `max_pairs` budget (default 45) caps this; traces exceeding it
degrade to adjacent-only comparison, which is strictly what the per-span path already
does. This bound is a deliberate guard, not a measured optimum.

## 5. Results

Each change is measured in isolation, so neither is credited with the other's effect.

| Configuration | Precision | Recall | F1 | FPR | TP/FP/FN/TN | Pairs compared | Pairs gated | Mean ms/case | Median ms/case |
| :--- | ---: | ---: | ---: | ---: | :---: | ---: | ---: | ---: | ---: |
| `baseline` — adjacent-only, no gate (as shipped) | 0.769 | 0.833 | 0.800 | 0.300 | 10/3/2/7 | 29 | 0 | 264.5 | 210.9 |
| `gate_only` — adjacent-only + relevance gate | 0.889 | 0.667 | **0.762** | 0.100 | 8/1/4/9 | 29 | 9 | 262.6 | 209.7 |
| `nway_gated` — all-pairs + gate (current default) | **0.923** | **1.000** | **0.960** | 0.100 | 12/1/0/9 | 38 | 12 | 341.5 | 201.9 |

Total benchmark wall time: 23.9 s. Headline latency spread: min 176.1 ms, median 201.9 ms,
mean 341.5 ms, max 1240.5 ms — the mean is pulled well above the median by the 4-agent
cases, which run 6 comparisons instead of 1.

### 5.1 The relevance gate on its own is a regression

**`gate_only` scores worse than the untouched baseline on F1: 0.800 → 0.762.**

It did exactly what it was designed to do — precision 0.769 → 0.889, FPR 0.300 → 0.100 —
but recall fell 0.833 → 0.667. The cause is §3.2: the gate correctly suppressed the
topic-mismatch firings that were accidentally producing true positives on `ma_04` and
`ma_05`. Removing the accident exposes the real miss underneath.

Had the gate shipped alone, this benchmark would have reported it as a failure. It is
only in combination with N-way comparison — which then detects those two cases on the
correct pair — that either change pays off. This is recorded because the isolated
measurement is more informative than the combined one, and because the combined number
alone would have concealed it.

### 5.2 What the combined configuration fixed

- **Architectural misses: 2 → 0.** `ma_06` and `ma_07` are now detected.
- **Wrong-pair true positives: 2 → 0.**
- **Strict recall: 0.667 → 1.000.** All 12 labelled conflicts are now flagged on the
  labelled pair. On this dataset there is no longer a gap between headline and strict
  recall.
- **FPR: 0.300 → 0.100.**
- **Cost: +31% comparisons (29 → 38), +29% mean latency (264 → 342 ms).**

## 6. What is still wrong, and what is not being chased

**`ma_13` remains a false positive.** Similarity 0.647 clears the 0.40 floor, and DeBERTa
scores the pair at 0.984 contradiction, so neither mechanism catches it. The two outputs
state the same fact with different time formats ("the 14:00 deployment" / "the deploy that
shipped at 2 PM"). Catching this would require either special-casing time normalisation or
raising the floor above 0.647 — and raising it there would also suppress `ma_21` (0.433)
and `ma_22` (0.457), both genuine contradictions. This is a model limitation, and the
trade is not favourable. It is left standing, in line with the reasoning in
`TOOL_CLAIM_VALIDATOR_REPORT.md` §3 about not growing pattern lists until a simple
component becomes an untested reimplementation of something else.

**An expectation in the dataset was wrong, and is reported rather than quietly corrected.**
Three cases (`ma_20`, `ma_21`, `ma_22`) were written as "known limitations" — implicit
contradictions expected to be missed, included specifically to prevent this benchmark
scoring a self-congratulatory 1.0. Examples: "no records were dropped during
preprocessing" against "reduced the working set from 5,000 rows down to 4,150"; "the first
time this fault has ever been reported" against "found four prior tickets describing this
same fault". **All three were detected**, at 0.970, 0.994 and 0.987. DeBERTa handled
implicit and numeric contradiction better than the author predicted. The category label in
the dataset records what these cases were constructed to be; this paragraph records what
they actually turned out to measure. The consequence is that this benchmark contains
**no case that the final configuration misses**, which is a weakness of the dataset, not a
strength of the engine — a harder set would very likely find failures.

**One labelling error was found and fixed.** `ma_22` was marked `adjacent: false` while
containing only two agents, which are necessarily adjacent. Metadata only; it affected
miss-type classification, not scoring, and the case was correctly predicted either way.

## 7. Test coverage added

`tests/test_disagreement.py` grew from 4 tests to 16. The 4 pre-existing tests are
unchanged. The 12 new tests cover the detection paths that previously had none:

- Relevance gate: contradiction on-topic flagged; agreement on-topic not flagged; high
  contradiction off-topic gated; gate disabling; fail-open when similarity is unavailable;
  boundary behaviour immediately below and exactly at the floor.
- N-way: minimum-input handling; **non-adjacent pair comparison (a direct regression test
  for the `ma_06`/`ma_07` architectural miss)**; all-pairs-gated aggregation; `max_pairs`
  degradation to adjacent-only; max-score aggregation.

These tests patch the NLI and similarity calls rather than loading model weights. This is
deliberate: model behaviour is measured empirically by the benchmark against labelled
data, whereas gating, pairing and aggregation are deterministic logic that belongs in a
fast unit test. Loading real models would add roughly 20 s to a 2 s suite and would be
testing DeBERTa rather than this module.

Full suite after these changes: **113 passed** (from 101), 2.37 s, no regressions.

## 9. Follow-up: N-way wired into the live pipeline (2026-08-26)

The §8 open item is closed. The pipeline now compares each arriving span against the
earlier agents of **its own trace**, so a contradiction between non-adjacent agents is
detected in production, not only in this benchmark.

**Design.** A trace-completion hook was considered and rejected — nothing in the system
signals trace completion (`Trace.status` defaults to `"running"` and `ingest.py` never
sets it otherwise), so it would have meant inventing a protocol the SDK does not send.
Instead the comparison is incremental: `evaluate_against_prior_agents()`
(`backend/app/services/disagreement.py`) compares one span against the agents preceding
it, which adds exactly the N−1 pairs that span introduces. Cumulatively a trace still
reaches full N(N−1)/2 coverage, whereas calling `evaluate_trace_disagreements()` per span
would re-compare every prior pair and cost O(N³).

`result.disagreement` remains a single `DisagreementResult` — the worst contradicting
pair — so risk aggregation, the `Evaluation` row, and alerting were not changed.

**A separate real bug was fixed by the same change.** `_evaluate_spans_background`
tracked `prev_span` as "the previous span in the batch" with no `trace_id` check, while
the SDK batches a flat buffer with no trace grouping. A batch carrying two interleaved
traces therefore compared an agent against an agent **from a different trace**. The
replacement query is scoped to `trace_id` and restricted to spans ordering before the
current one — the latter because every batch span is already committed when evaluation
runs, so an unrestricted query would evaluate each pair twice.

**Verified against the real database and real model weights** (not the monkeypatched
stubs the unit tests use), on a 4-agent trace whose conflict is between agents 1 and 4,
with a second interleaved trace present to test scoping:

| | Result |
| :--- | :--- |
| Prior lookup per span | Exactly the preceding agents, in order; zero leakage from the interleaved trace |
| N-way path | `triager → escalator`, score **0.9999**, flagged |
| Adjacent-only path (previous behaviour) | `analyst → escalator`, score **0.0042**, not flagged |

That is the `ma_06` failure shape reproduced end-to-end and shown fixed.

**Consequences to watch.** The disagreement score is now the maximum over all prior
pairs rather than one upstream pair, so it can only increase — composite risk and
therefore alert volume will rise on multi-agent traces. Cost is O(N²) per trace in a
background thread pool, bounded by a 12-prior-per-span budget, plus one database query
per span. Tests: 113 → 121.
